# KCCB kickの短時間poll

`a4kf=1`（長い別名 `a04br3-kccb-fast=1`）は機種固有の実験設定で、既定オフ。通常のkickと
combined geometry/fragment kickのみ、実行済みカウンタを再確認し、未完了なら
10μsのdelayを最大5回挟んで、従来の1ms sleepに戻る。delayの指定合計は
最大50μsだが、cache操作とスケジューリングで経過時間は増え得る。最初の確認で完了
していれば待機せず、実行済みカウンタの同じ目標値を用いる。MMU cache、
cleanupなど他のコマンドやtimeout 0には短時間pollを行わない。

根拠は511a初回起動の、最初116回のKCCB区間が累計139.612538msという観測と、
初回read後に完了したkickを1ms sleepが終わるまで検出できない実装上の条件。
この区間には他の処理とスケジュール待ちも含まれ、firmware完了時刻は未測定。
実機のfirmwareが50μs以内に完了する保証はなく、CPU負荷・充電への影響も
未測定。ホスト試験による早期発見はロジックの検証で、実機改善の証明ではない。
最大5回のdelay後はsleepに戻す。既存のtimeoutはsleep回数で数えており、
短時間poll分はそのtimeoutに加わる。submit経路では `gJobs.lock` を保持したまま
この短時間pollを行うため、待機中の他スレッドにも影響し得る。

現行all-task基準 `f2dee958a180ae6fee7b84a44baf9d74dcd22aff` の記録済み
bootargsは1006 bytesで、この長い起動引数を追加すると1025 bytesとなり、
DarwinBootの1023-byte上限を超える。切り詰めて起動してはならない。
短縮別名を使うと全計測設定を維持したまま両群とも1013 bytesとなり、
末尾の `a4kf=0` / `a4kf=1` の1文字だけが異なる。両群共通の診断削除でも
短縮できるが、既存計測条件が変わるため採用しない。
`scripts/a04br3-kccb-fast-profiles.py` は固定baselineの実引数SHA-256を検証して
ペアを生成する。実FAT引数・同一kernel・GPU・Dataその他の構成は別途検証が必要。
aliasと長い名称の重複や併記、不正値はすべてオフ。正確な `0` / `1` のみ受理し、
以前の長い名称も同じ厳格な規則を使う。画像生成・実機試験は本変更に含まれない。
KICK失敗時のエラー伝播とFW遅延完了時の資源寿命には別途P1レビューがあり、
この性能候補の実機投入前に解決と独立レビューが必要。

根本的にはLinuxのような非同期slot予約・完了通知と、全enqueue経路の予約および
失敗処理が必要。診断対象の待機を成功したことにしたり、GPUのfenceを先にsignal
したりしない。実機では比較前後のKCCB所要時間、CPU、給電、正常な描画と
fence結果を確認する。設定を含まない通常bootは従来どおり。
