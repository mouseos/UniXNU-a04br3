# 署名準備 read-batch の比較プロファイル

`scripts/a04br3-read-batch-profiles.py` は保存済み boot manifest の
`kernel_args` から2種類の引数を生成する。両方で `native-root-timing=1` を
有効にし、バッチ側だけに既存の `native-cs-read-batch=1` を加える。
`native-cs-coalesce` は指定しない。元の実験で使用した診断引数
`ecb=1`、`mb=2`、`a04br3-gio=6`、`native-io-trace=1` は両方から除く。
`ecb` と `mb` はメモリーコピー診断、`a04br3-gio` はGPU I/O診断、
`native-io-trace` はI/O重複の記録である。したがって2種類の間はバッチの
有無だけが異なるが、元の io-overlap-7fb 起動とは同一条件ではない。

保存済みmanifestでは通常側999 bytes、バッチ側1022 bytesで、後者は
終端NUL込み1023 bytes。タイミング用フラグを有効にしたカーネルが別途必要。
`RST hash` の `rc`、`rb`、`rn`、`on`、`dn`、`bat` と、実測区間の完了・
panic・再起動を比較する。診断の計時負荷、キャッシュ状態、ブート順序、
未完了区間は結果の解釈に含める。異なるboot間の集計値は同一処理量を保証
しない。比較には同一固定ソース・payload・初期条件を使う。

```sh
python3 scripts/a04br3-read-batch-profiles.py /path/to/manifest.json
python3 scripts/tests/test_read_batch_profiles.py
```

スクリプトは引数文字列を出力するだけで、bootを生成・書込みしない。
改ざん拒否のhost試験はXNU側の `check_native4k_page_validation.py` と
`check_root_read_batch.py` を使用する。実機性能や実機安全性は未検証。

検証時は対象PIDと完全な集計を対応付け、通常側の `bat=0` とバッチ側の
`bat>0` を確認する。`bat` は選択されたprepare呼出しの累積数であり、
常に1になる値ではない。対象処理量、終了エラーと全ブロック成功を併記する。
試行は少なくとも各3回、順序を交互にし、キャッシュ状態や起動順の差を記録
する。256 KiBバッファの確保も同時に変わるため、差をI/O回数だけの効果と
断定しない。低メモリ時の挙動も実機では未確認である。

## 比較の受入条件と初期条件

両方で同一のカーネル、署名付きpayload、データ領域、UEFI、診断設定を使い、
各イメージのmanifestとハッシュを保存する。起動順序は通常・バッチを交互に
し、同一の再起動手順と条件を記録する。再起動だけではデバイス側やファイル
システム側のキャッシュが消えたと決めつけず、温・冷状態を確認できない場合は
不明として扱う。各回の起動範囲、欠損、完了範囲、panicと次回preloaderを分離。
通常側 `bat=0`、バッチ側 `bat>0`、処理成功と署名対象量を確かめてから、
`rc`、`rb`、`rn`、`on`、`dn` と区間所要時間を比較する。集計が不完全、
対象量が大きく異なる、片方が途中で停止、またはバッチ未選択なら無効試行。
`bat>0` は一部で選択されたことだけを示し、全呼出しの選択を保証しない。

prepareのscratchは呼出しごとに通常16 KiB、バッチ256 KiBを `Z_WAITOK` で
確保する。並行2呼出しならscratchだけで32 KiB対512 KiB、さらに署名範囲に
応じたハッシュ配列が各呼出しに必要。並行数にこの機能独自の上限はなく、
低メモリ時の確保待ち・割当て圧力は計測前には分からない。先読みと確保の
双方を含む変更として評価し、読込要求数の減少だけを性能改善と判定しない。

バッチでは256 KiBを先読みしてから16 KiBごとに検証するため、先頭の不正
署名と後方の読込エラーが同時に存在する場合、通常側は `EBADEXEC`、バッチ側は
読込エラーを先に返し得る。どちらも配列を公開しないことをホスト試験するが、
実際の呼出し元のエラー再試行と端末上の安全性は別途確認が必要。

## 事前に固定する採否基準

最低3組の有効ペアで、同じ対象PID・完了範囲について両側の `rb` と対象
署名準備回数が完全一致し、通常側 `bat=0`、バッチ側 `bat=pc>0` を確認する。`pc` は失敗やno-opも
含むため、全prepareで選択されたことを確認できない集計はこの比較から除く。欠損・panic・再起動・処理失敗・
バッチ未選択・条件不一致は無効。対象範囲が同じか判定できない集計は性能
採否に使わない。`native-root-timing` 有効であることをbuild provenanceと
実際の完全な `RST hash` 記録の両方で確認する。

各ペアの署名準備`RST prep` の `pn` のバッチ/通常比を算出し、中央値0.95以下かつ
最大1.10以下を暫定の改善基準とし、全値・中央値・最小/最大を併記する。
外れ値を事後に削除しない。この少数試行は統計的な効果の確定ではない。
キャッシュ温度を確認できない場合はデータを探索結果として記録できるが、
改善の採否には使わない。バッチ固有の読込先行と追加メモリを含む評価であり、
過去の io-overlap-7fb 生データとの比較や読込回数だけの因果を主張しない。

固定XNUの `pexpert/pexpert/arm64/boot.h` は `BOOT_LINE_LENGTH` を1024、
`CommandLine` をその長さの配列として定義する。生成プロファイルは終端NUL
込み1024 bytes以内とし、device/UEFI側でもコピー時の長さと終端を別途検証
する。実際の起動時に渡された引数をUARTから照合できない場合は無効試行。

`RST` は `q`・`p`・`u` が同じ行を対応付けるが、複数行は一括の原子的
スナップショットではない。prepareが進行中に取得した集計は境界を確定できず、
完了後かつ収集が揃ったことを確認できない場合は採否対象から除外する。
